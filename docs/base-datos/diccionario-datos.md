# ClimaPlus – Diccionario de datos

**Proyecto:** ClimaPlus – Panel de clima y alertas ambientales
**Curso:** Desarrollo Web
**Fase:** 1 – Arquitectura y diseño de base de datos
**Motor:** PostgreSQL 16 (D-05)
**Acceso a datos:** Entity Framework Core con proveedor Npgsql
**Estado:** modelo aprobado (decisiones D-01 a D-13), con las enmiendas E-02 y E-03 (2026-10-28) en `consulta_clima`

---

## Decisiones aprobadas que afectan a la base de datos

| Código | Decisión | Efecto en el modelo |
|---|---|---|
| D-01 | Autenticación propia con JWT y `PasswordHasher` | Se usa la tabla `usuario`; no se crean tablas de ASP.NET Core Identity ni se guardan tokens |
| D-02 | Alertas al consultar clima actual o al recibir una lectura del ESP32 | `alerta` tiene exactamente un origen: `id_consulta` o `id_lectura` |
| D-03 | El historial distingue consultas `ACTUAL` y `PRONOSTICO` (**MODIFICADA por E-03**) | Columna `consulta_clima.tipo_consulta`; las mediciones solo se guardan en columnas en consultas `ACTUAL`; el pronóstico se guarda normalizado en `consulta_clima.detalle` |
| D-04 | Consulta pública de clima y pronóstico (**MODIFICADA por E-02**) | Las consultas anónimas se registran con `consulta_clima.id_usuario` NULL y no aparecen en ningún historial personal |
| D-05 | PostgreSQL 16 | Permite `UNIQUE NULLS NOT DISTINCT` |
| D-06 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Estrategia de identificadores de todas las tablas |
| D-07 | Coordenadas con 4 decimales | `NUMERIC(7,4)` y `NUMERIC(8,4)` con `UNIQUE (latitud, longitud)` |
| D-08 | Lluvia `BOOLEAN`, luz 0–100 % | Tipos de `lectura_sensor.lluvia` y `lectura_sensor.luz` |
| D-09 | Anti-duplicado de alertas de 1 hora | Regla RN-BD-27, aplicada en el backend |
| D-10 | Se elimina `operador` | El tipo de alerta define la comparación |
| D-11 | `dispositivo.activo BOOLEAN` | Reemplaza a `estado` |
| D-12 | Se mantiene `dispositivo.ultima_conexion` | Redundancia controlada, actualizada al recibir cada lectura |
| D-13 | Se mantiene `alerta.mensaje` | Texto de notificación generado por el backend y conservado como historial |

## Convenciones generales

| Aspecto | Convención |
|---|---|
| Nombres | `snake_case`, tablas en singular |
| Identificadores | `BIGINT GENERATED BY DEFAULT AS IDENTITY` en todas las tablas |
| Fechas | `TIMESTAMPTZ`, almacenadas en UTC; el frontend las presenta en hora local (America/Guatemala) |
| Valores de dominio | `VARCHAR` con restricción `CHECK` (no se usan tipos `ENUM` nativos de PostgreSQL) |
| Unidades | Temperatura en °C, velocidad del viento en m/s, humedad y luz en % |
| Borrado de usuarios y dispositivos | Lógico (`activo = FALSE`); el borrado físico queda restringido cuando existe historial |
| Secretos | Nunca en texto plano: `password_hash` (hash con sal) y `api_key_hash` (SHA-256) |

### Dominios de valores

| Dominio | Valores permitidos | Usado en |
|---|---|---|
| Rol | `USUARIO`, `ADMINISTRADOR` | `usuario.rol` |
| Tipo de alerta | `LLUVIA`, `TEMPERATURA_ALTA`, `TEMPERATURA_BAJA` | `configuracion_alerta.tipo`, `alerta.tipo` |
| Estado de alerta | `NUEVA`, `LEIDA` | `alerta.estado` |
| Tipo de consulta | `ACTUAL`, `PRONOSTICO` | `consulta_clima.tipo_consulta` |

### Semántica de los tipos de alerta

| Tipo | Condición que dispara la alerta | Umbral |
|---|---|---|
| `TEMPERATURA_ALTA` | temperatura medida **>** `valor_umbral` | Obligatorio |
| `TEMPERATURA_BAJA` | temperatura medida **<** `valor_umbral` | Obligatorio |
| `LLUVIA` | OpenWeather: `codigo_condicion` en grupos 2xx, 3xx o 5xx · ESP32: `lluvia = TRUE` | No aplica (`NULL`) |

El operador de comparación queda determinado por el tipo; por eso no se almacena.

## 1. Tabla `usuario`

Personas registradas en el sistema, con su rol y estado.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_usuario | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador del usuario |
| nombre | VARCHAR(100) | NOT NULL, CHECK (longitud recortada > 0) | No | Nombre para mostrar |
| correo | VARCHAR(150) | NOT NULL, UNIQUE, CHECK (`correo = lower(correo)`) | No | Correo de inicio de sesión, guardado en minúsculas |
| password_hash | VARCHAR(255) | NOT NULL | No | Hash con sal de la contraseña; nunca la contraseña |
| rol | VARCHAR(20) | NOT NULL, DEFAULT `'USUARIO'`, CHECK (dominio Rol) | No | Rol de autorización |
| activo | BOOLEAN | NOT NULL, DEFAULT `TRUE` | No | `FALSE` impide iniciar sesión (baja lógica) |
| fecha_creacion | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha y hora de registro |

## 2. Tabla `ubicacion`

Catálogo compartido de ubicaciones meteorológicas. Se crea una fila la primera vez que alguien usa una ubicación (consulta, favorito, regla de alerta o dispositivo) y luego se reutiliza. No pertenece a ningún usuario.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_ubicacion | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador de la ubicación |
| nombre | VARCHAR(100) | NOT NULL | No | Nombre de la ciudad o localidad (p. ej. "Cobán") |
| region | VARCHAR(100) | — | Sí | Departamento o estado (p. ej. "Alta Verapaz"); distingue ciudades homónimas |
| pais | CHAR(2) | NOT NULL, CHECK (`pais ~ '^[A-Z]{2}$'`) | No | Código de país ISO 3166-1 alfa-2 (p. ej. "GT") |
| latitud | NUMERIC(7,4) | NOT NULL, CHECK (entre -90 y 90), UNIQUE (latitud, longitud) | No | Latitud redondeada a 4 decimales (~11 m) |
| longitud | NUMERIC(8,4) | NOT NULL, CHECK (entre -180 y 180), UNIQUE (latitud, longitud) | No | Longitud redondeada a 4 decimales |
| fecha_creacion | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha en que se registró la ubicación |

**Restricciones de tabla:** `UNIQUE (latitud, longitud)` evita registrar dos veces la misma ubicación.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |

**Restricciones de tabla:** `UNIQUE (id_usuario, id_ubicacion)`.

## 4. Tabla `configuracion_alerta`

Reglas de alerta definidas por cada usuario.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_configuracion | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador de la regla |
| id_usuario | BIGINT | FK → usuario, ON DELETE CASCADE | No | Dueño de la regla |
| id_ubicacion | BIGINT | FK → ubicacion, ON DELETE RESTRICT | Sí | Ubicación a la que aplica; `NULL` = todas las ubicaciones del usuario |
| tipo | VARCHAR(20) | NOT NULL, CHECK (dominio Tipo de alerta) | No | Tipo de alerta |
| valor_umbral | NUMERIC(5,2) | CHECK (entre -50 y 60), CHECK de coherencia con `tipo` | Sí | Umbral en °C; `NULL` cuando `tipo = 'LLUVIA'` |
| activa | BOOLEAN | NOT NULL, DEFAULT `TRUE` | No | Permite pausar la regla sin eliminarla |
| fecha_creacion | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha de creación |

**Restricciones de tabla:**

- `UNIQUE NULLS NOT DISTINCT (id_usuario, id_ubicacion, tipo)`: una sola regla por usuario, ubicación y tipo (incluida una sola regla global por tipo).
- CHECK de coherencia: (`tipo = 'LLUVIA'` y `valor_umbral IS NULL`) o (`tipo <> 'LLUVIA'` y `valor_umbral IS NOT NULL`).

## 5. Tabla `consulta_clima`

Registro de todas las consultas meteorológicas (D-03 y D-04, modificadas por E-03 y E-02). Los datos externos se guardan antes de mostrarse (guía oficial, sección 4).

- En una consulta `ACTUAL` se guarda una fotografía de las condiciones del momento, porque OpenWeather no permite reconstruirlas después: las 6 mediciones en columnas y los datos extra de M04 en `detalle`.
- En una consulta `PRONOSTICO` las columnas de medición quedan en NULL y el pronóstico normalizado (días y bloques de 3 horas) se guarda en `detalle` (E-03, RN-BD-43).
- Las consultas anónimas (sin sesión) se registran con `id_usuario` NULL (E-02). No aparecen en ningún historial personal ni generan alertas (RN-BD-13, RN-BD-42).

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_consulta | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador de la consulta |
| id_usuario | BIGINT | FK → usuario, ON DELETE RESTRICT | Sí | Usuario autenticado que realizó la consulta; NULL = visitante sin sesión (E-02) |
| id_ubicacion | BIGINT | FK → ubicacion, ON DELETE RESTRICT | No | Ubicación consultada |
| tipo_consulta | VARCHAR(20) | NOT NULL, CHECK (dominio Tipo de consulta) | No | `ACTUAL` o `PRONOSTICO` |
| temperatura | NUMERIC(5,2) | CHECK (entre -90 y 60), CHECK de coherencia con `tipo_consulta` | Sí | Temperatura en °C; solo en `ACTUAL` |
| sensacion_termica | NUMERIC(5,2) | CHECK (entre -90 y 70), CHECK de coherencia | Sí | Sensación térmica en °C; solo en `ACTUAL` |
| humedad | SMALLINT | CHECK (entre 0 y 100), CHECK de coherencia | Sí | Humedad relativa en % (OpenWeather la entrega como entero); solo en `ACTUAL` |
| velocidad_viento | NUMERIC(5,2) | CHECK (>= 0), CHECK de coherencia | Sí | Velocidad del viento en m/s; solo en `ACTUAL` |
| codigo_condicion | SMALLINT | CHECK (entre 200 y 899), CHECK de coherencia | Sí | Código de condición de OpenWeather (`weather[0].id`); permite detectar lluvia; solo en `ACTUAL` |
| descripcion_condicion | VARCHAR(100) | CHECK de coherencia | Sí | Descripción en español (p. ej. "lluvia ligera"); solo en `ACTUAL` |
| detalle | JSONB | CHECK (objeto JSON), CHECK (obligatorio en `PRONOSTICO`) | Sí | Datos normalizados sin columna propia (E-03): en `ACTUAL`, los datos extra de M04; en `PRONOSTICO`, los días y bloques de M05. Formato: sección 6 de `docs/enmiendas/E-02-E-03-especificacion-tecnica.md`. Nunca contiene la respuesta cruda de OpenWeather ni la API key |
| fecha_consulta | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha y hora de la consulta |

**Restricciones de tabla:**

- CHECK de coherencia entre tipo y mediciones (`ck_consulta_clima_mediciones_tipo`):
  - `tipo_consulta = 'ACTUAL'` y `num_nonnulls(temperatura, sensacion_termica, humedad, velocidad_viento, codigo_condicion, descripcion_condicion) = 6`, **o**
  - `tipo_consulta = 'PRONOSTICO'` y `num_nonnulls(...) = 0`.
- `ck_consulta_clima_detalle_objeto` (E-03): `detalle IS NULL OR jsonb_typeof(detalle) = 'object'`.
- `ck_consulta_clima_detalle_pronostico` (E-03, RN-BD-43): `tipo_consulta <> 'PRONOSTICO' OR detalle IS NOT NULL`.

`consulta_clima` tiene 12 columnas y 9 restricciones CHECK; el modelo completo, 26 CHECK.

## 6. Tabla `dispositivo`

Dispositivos ESP32 registrados por los usuarios.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|

| nombre | VARCHAR(100) | NOT NULL, UNIQUE (id_usuario, nombre) | No | Nombre descriptivo (p. ej. "Patio casa") |

## 7. Tabla `lectura_sensor`

Mediciones físicas enviadas por un ESP32.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_lectura | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador de la lectura |
| id_dispositivo | BIGINT | FK → dispositivo, ON DELETE RESTRICT | No | Dispositivo que produjo la lectura |
| temperatura | NUMERIC(5,2) | CHECK (entre -40 y 85, rango del BME280) | Sí | Temperatura en °C |
| humedad | NUMERIC(5,2) | CHECK (entre 0 y 100) | Sí | Humedad relativa en % |
| lluvia | BOOLEAN | — | Sí | `TRUE` si el sensor detecta lluvia |
| luz | SMALLINT | CHECK (entre 0 y 100) | Sí | Nivel de luz normalizado en % (a partir del LDR) |
| fecha_lectura | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha y hora asignada por el servidor al recibir la lectura |

**Restricciones de tabla:** `CHECK (num_nonnulls(temperatura, humedad, lluvia, luz) >= 1)`: una lectura debe contener al menos una medición.

## 8. Tabla `alerta`

Alertas generadas cuando una medición cumple una regla activa del usuario (D-02). Cada alerta conserva el tipo, el umbral y el mensaje vigentes en ese momento, para que el historial no cambie si después se edita o elimina la regla.

| Campo | Tipo PostgreSQL | Restricción | Permite NULL | Descripción |
|---|---|---|---|---|
| id_alerta | BIGINT | PK, IDENTITY (GENERATED BY DEFAULT) | No | Identificador de la alerta |
| id_usuario | BIGINT | FK → usuario, ON DELETE RESTRICT | No | Usuario destinatario |
| id_ubicacion | BIGINT | FK → ubicacion, ON DELETE RESTRICT | No | Ubicación donde se detectó la condición |
| id_consulta | BIGINT | FK → consulta_clima, ON DELETE RESTRICT | Sí | Consulta de clima `ACTUAL` que originó la alerta |
| id_lectura | BIGINT | FK → lectura_sensor, ON DELETE RESTRICT | Sí | Lectura del ESP32 que originó la alerta |
| tipo | VARCHAR(20) | NOT NULL, CHECK (dominio Tipo de alerta) | No | Tipo de alerta |
| valor_detectado | NUMERIC(5,2) | CHECK de coherencia con `tipo` | Sí | Temperatura medida en °C; `NULL` en alertas de lluvia |
| valor_umbral | NUMERIC(5,2) | CHECK de coherencia con `tipo` | Sí | Umbral vigente al generarse; `NULL` en alertas de lluvia |
| mensaje | VARCHAR(255) | NOT NULL | No | Texto legible de la alerta, generado por el backend al crearla (p. ej. "Cobán: 33.4 °C supera tu umbral de 32 °C") |
| estado | VARCHAR(20) | NOT NULL, DEFAULT `'NUEVA'`, CHECK (dominio Estado de alerta) | No | Estado de lectura de la alerta |
| fecha_generacion | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | No | Fecha y hora de generación |

**Restricciones de tabla:**

- `CHECK (num_nonnulls(id_consulta, id_lectura) = 1)`: la alerta proviene de una consulta o de una lectura, nunca de ambas ni de ninguna. El origen (OpenWeather o ESP32) se deduce de cuál de los dos campos tiene valor.
- CHECK de coherencia: (`tipo = 'LLUVIA'` y `valor_detectado IS NULL` y `valor_umbral IS NULL`) o (`tipo <> 'LLUVIA'` y `valor_detectado IS NOT NULL` y `valor_umbral IS NOT NULL`).
- Reglas aplicadas en el backend (no expresables con CHECK): `id_consulta` solo puede apuntar a una consulta `ACTUAL` del mismo usuario de la alerta, nunca a una consulta anónima (RN-BD-42); no se crea una alerta si ya existe otra del mismo usuario, ubicación y tipo generada en los últimos 60 minutos (D-09).
